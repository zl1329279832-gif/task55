# 订单-房态-库存一致性设计说明

> 版本: v1.0 — 基于当前代码（未修改 Service 实现）
>
> 适用范围: `OrderServiceImpl` · `CheckInServiceImpl` · `RoomInventoryServiceImpl` · `RoomTypeServiceImpl`

---

## 0. 问题背景

开发侧反馈："用户付完款列表显示有空房（`room_type.rest` > 0），但入住登记又报占用冲突。"

根因：系统存在 **两套并行库存体系**——聚合余量 `room_type.rest` 与按日房态 `room_inventory`，二者写入时机和并发控制策略不同，
在高并发或历史数据场景下可能出现不一致。本文档将两套体系的读写关系、状态迁移和并发语义完整归档，
作为后续修 bug 和代码评审的单一事实来源。

## 1. 数据模型速查

### 1.1 两套库存体系

| 体系 | 表 / 字段 | 粒度 | 含义 |
|------|-----------|------|------|
| **聚合余量** | `room_type.rest` | 房型级别（不分日期） | "该房型还能接多少单"的快查字段，前端列表展示用 |
| **按日房态** | `room_inventory` (UK: `type_id` + `inv_date`) | 房型 × 日期 | 真实可售 / 已订 / 已住 库存，支持跨天入住、超售防护 |
| **物理房态** | `room_info.room_status` | 单个房间 | 具体哪间房被分配给哪位客人 |

### 1.2 room_inventory 可订量公式

```
available = total - ordered - occupied - reserved - maintenance
```

| 字段 | 含义 |
|------|------|
| `total` | 该房型当天物理房间总数（从 `room_info` 统计） |
| `ordered` | 已付款、待入住的订单占用数 |
| `occupied` | 已办理入住、正在使用房间的占用数 |
| `reserved` | 操作员手动保留（如协议客户锁房） |
| `maintenance` | 维修锁房 |

### 1.3 room_inventory 行懒初始化

库存行并非预创建，而是在首次被访问时由 `ensureInventoryRow()` 通过 `INSERT IGNORE`（利用 UK `uk_type_date` 的幂等性）按需写入，
`total` 取自 `SELECT COUNT(*) FROM room_info WHERE type_id = ?`。

## 2. 四步操作读写矩阵

以下矩阵列出 `payOrder` / `cancelOrder` / `checkIn` / `checkOut` 对三套库存的 **实际读写行为**。

> 读 = SELECT 后判断 / 写 = UPDATE 或 INSERT。"—" 表示该操作不涉及此字段。

### 2.1 room_inventory 读写矩阵

| 操作 | `ordered` | `occupied` | `available`（计算列） | 底层 SQL ID |
|------|-----------|------------|----------------------|-------------|
| **payOrder** | **写** +1（逐天） | — | 读（guard: ≥1） | `incrementOrdered` |
| **cancelOrder**（仅 PAID） | **写** −1（逐天） | — | —（隐式 +1） | `decrementOrdered` |
| **cancelOrder**（UNPAID） | — | — | — | （不触碰 inventory） |
| **checkIn** | **写** −1（逐天） | **写** +1（逐天） | 不变（净效果 0） | `convertOrderedToOccupied` |
| **checkOut** | — | **写** −1（逐天） | —（隐式 +1） | `decrementOccupied` |

### 2.2 room_type.rest 读写矩阵

| 操作 | `rest` 变化 | 实现方式 | 并发保护 |
|------|-------------|----------|----------|
| **payOrder** | −1 | read → modify → write（`updateRest(typeId, -1)`） | **无**（⚠ 无乐观锁 / 无 `SELECT FOR UPDATE`） |
| **cancelOrder**（仅 PAID） | +1 | read → modify → write（`updateRest(typeId, +1)`） | **无** |
| **cancelOrder**（UNPAID） | — | — | — |
| **checkIn** | — | 不触碰（payOrder 已扣） | — |
| **checkOut** | +1 | read → modify → write（`updateRest(typeId, +1)`） | **无** |

### 2.3 room_info.room_status 读写矩阵

| 操作 | `room_status` 变化 | 实现方式 | 并发保护 |
|------|-------------------|----------|----------|
| **payOrder** | — | — | — |
| **checkIn** | AVAILABLE → IN_USE | CAS: `updateStatusByIdAndCurrentStatus` | **有**（WHERE room_status = 旧值） |
| **checkOut** | IN_USE → AVAILABLE | 直接 UPDATE | 无（依赖业务串行） |

### 2.4 order_info.order_status 读写矩阵

| 操作 | 前置状态 | 目标状态 | 并发保护 |
|------|---------|---------|----------|
| **payOrder** | UNPAID(0) | PAID(1) | **无**（⚠ 无乐观锁） |
| **cancelOrder** | UNPAID(0) 或 PAID(1) | WAS_CANCELED(-1) | **无** |
| **checkIn** | PAID(1) | CHECK_IN(2) | **无** |
| **checkOut** | — | **不变更**（停留在 CHECK_IN） | — |

## 3. 库存状态迁移图

### 3.1 room_inventory 生命周期

```
                        ┌─────────────────────────────────────────┐
                        │            payOrder()                   │
                        │   available ──→ ordered                 │
                        │   (available - 1, ordered + 1)          │
                        └────────────┬────────────────────────────┘
                                     │
                  ┌──────────────────┼──────────────────┐
                  │                                     │
           cancelOrder()                          checkIn()
        ordered ──→ available              ordered ──→ occupied
       (ordered - 1, available + 1)    (ordered - 1, occupied + 1)
                                              │
                                         checkOut()
                                      occupied ──→ available
                                     (occupied - 1, available + 1)
```

关键不变量：
- `available + ordered + occupied + reserved + maintenance = total`（任何时刻恒成立）
- `checkIn` 是 **零和转换**：`available` 不变，只是把"待入住"挪到"正在住"

### 3.2 room_type.rest 生命周期

```
  payOrder()         cancelOrder(PAID)       checkOut()
  rest − 1    ←──→    rest + 1                rest + 1
                  (反向恢复)               (退房恢复)
```

> ⚠ **设计要点**：`rest` 在 `payOrder` 扣减、在 `checkOut` 恢复，但 `cancelOrder(PAID)` 也会恢复。
> `checkIn` 不触碰 `rest`，因为库存已在付款时扣除。

### 3.3 订单状态迁移

```
                 ┌──── cancelOrder() ────→ WAS_CANCELED(-1)
                 │                              ↑
  UNPAID(0) ──payOrder()──→ PAID(1) ──cancelOrder()──→ WAS_CANCELED(-1)
                                    │
                               checkIn()
                                    ↓
                               CHECK_IN(2)
                                    │
                               checkOut()
                                    ↓
                              ⚠ 仍为 CHECK_IN(2)
                              （无 CHECK_OUT 状态）
```

## 4. occupyForCheckIn 旧订单兼容分支

### 4.1 问题场景

`room_inventory` 是后期引入的表（见 `sql/V1__add_room_inventory.sql`）。
系统上线前已存在的 PAID 订单，其对应的 `(type_id, inv_date)` 在 `room_inventory` 中可能 **没有记录行**，
或者记录行的 `ordered = 0`（因为付款时还没有 inventory 逻辑）。

如果 `checkIn` 对这类订单执行 `convertOrderedToOccupied`（SQL 要求 `WHERE ordered >= 1`），
会导致 `affected = 0` 并误判为"入住失败"。

### 4.2 兼容逻辑（当前实现）

```java
// RoomInventoryServiceImpl.occupyForCheckIn()
RoomInventory inv = inventoryMapper.selectByTypeAndDate(typeId, date);

if (inv == null || inv.getOrdered() == null || inv.getOrdered() < 1) {
    // 无库存行或无 ordered 占用：旧订单（系统上线前），优雅跳过
    success = true;   // ← 视为成功，不阻断 checkIn
    break;
}

// 正常路径：ordered--, occupied++
int affected = inventoryMapper.convertOrderedToOccupied(typeId, date, inv.getVersion());
```

### 4.3 行为矩阵

| 条件 | 行为 | 含义 |
|------|------|------|
| `inv == null` | `success = true`, 跳过 | 库存行不存在（上线前订单，从未触发懒初始化） |
| `inv.ordered == null` | `success = true`, 跳过 | 库存行存在但 ordered 字段为 NULL（脏数据容错） |
| `inv.ordered < 1` | `success = true`, 跳过 | 库存行存在但 ordered = 0（旧订单付款时未写 inventory） |
| `inv.ordered >= 1` 且版本匹配 | `convertOrderedToOccupied` | 正常路径：ordered → occupied 转换 |
| `inv.ordered >= 1` 且版本冲突 | 重试（最多 3 次） | 乐观锁冲突，重试后成功或失败 |

### 4.4 同样的兼容逻辑也出现在 releaseForCheckOut

```java
// RoomInventoryServiceImpl.releaseForCheckOut()
if (inv == null || inv.getOccupied() == null || inv.getOccupied() < 1) {
    break;  // 旧数据优雅跳过
}
```

> ⚠ **副作用**：如果一笔正常订单因并发异常导致 `ordered` 被意外清零，`occupyForCheckIn` 的兼容分支也会"静默成功"，
> 导致入住后 `occupied` 未正确 +1，退房时 `releaseForCheckOut` 同样静默跳过——该房间的库存将永久少计 1。

## 5. 并发控制与乐观锁语义

### 5.1 room_inventory 乐观锁机制

每条 `room_inventory` 行有一个 `version INT DEFAULT 0` 字段。所有写操作都携带版本条件：

```sql
-- 以 incrementOrdered 为例
UPDATE room_inventory
SET ordered = ordered + 1, version = version + 1, update_time = NOW()
WHERE type_id = #{typeId} AND inv_date = #{invDate}
  AND version = #{version}                          -- 乐观锁
  AND (total - ordered - occupied - reserved - maintenance) >= 1  -- 库存 guard
```

当 `affected = 0` 时，有两种可能：
1. **版本冲突**：另一个事务已修改该行并推进了 version → 应重试
2. **库存不足**：available < 1，真正售罄 → 不应重试

### 5.2 optimisticIncrementOrdered 重试策略

```java
private boolean optimisticIncrementOrdered(int typeId, Date date) {
    for (int attempt = 0; attempt < MAX_RETRY; attempt++) {  // MAX_RETRY = 3
        RoomInventory inv = inventoryMapper.selectByTypeAndDate(typeId, date);
        if (inv == null) {
            ensureInventoryRow(typeId, date);
            inv = inventoryMapper.selectByTypeAndDate(typeId, date);
        }
        if (inv == null || inv.getAvailable() < 1) {
            return false;   // 真正售罄，不重试
        }
        int affected = inventoryMapper.incrementOrdered(typeId, date, inv.getVersion());
        if (affected == 1) return true;
        // affected == 0 且 available >= 1 → 版本冲突，进入下次重试
    }
    return false;  // 重试耗尽
}
```

**失败语义**：
- 返回 `false` 有两种根因：**售罄**（available < 1）或 **重试耗尽**（3 次版本冲突）
- 上层 `occupyForOrder` 对二者 **不做区分**，统一返回 `-2`（库存不足）
- 对于调用方 `payOrder`，`-2` 意味着"该房型在该日期范围内无法承接此订单"

### 5.3 跨天订单的逐天占用与回滚

```java
// occupyForOrder: 逐天占用，任一天失败则回滚已占用的天
for (int i = 0; i < days; i++) {
    boolean success = optimisticIncrementOrdered(typeId, addDays(startDate, i));
    if (!success) {
        // 回滚：释放第 0 ~ i-1 天已占用的 ordered
        for (int j = 0; j < i; j++) {
            retryingDecrementOrdered(typeId, addDays(startDate, j));
        }
        return -2;
    }
}
```

这保证了 **跨天订单的原子性**：要么所有天都占用成功，要么全部回滚。

### 5.4 ConcurrencyTest 验证场景

| 测试方法 | 验证点 | 依赖的并发控制 |
|---------|--------|---------------|
| `testConcurrentPayOrder_onlyOneSucceeds` | 5 线程抢 3 间房，成功数 ≤ 3，`rest = 初始值 − 成功数` | `incrementOrdered` 的 available guard + 乐观锁 |
| `testConcurrentCheckIn_noDuplicateRoom` | 3 笔已付款订单并发入住，不出现重复房间分配 | `updateStatusByIdAndCurrentStatus` 的 CAS |
| `testCrossDayCheckIn_inventoryCorrect` | 3 天订单：付款后逐天 ordered=1；入住后 ordered=0, occupied=1；退房后 occupied=0 | `convertOrderedToOccupied` + `decrementOccupied` |
| `testCancelReleasesInventory_correctlyAfterPay` | 2 天订单：付款后 rest 减 1、ordered=1；取消后 rest 恢复、ordered=0 | `decrementOrdered` + `updateRest(+1)` |

### 5.5 已知并发弱点（未在测试中覆盖）

| 风险点 | 位置 | 影响 | 当前测试覆盖 |
|--------|------|------|-------------|
| **room_type.rest 无锁** | `RoomTypeServiceImpl.updateRest()` | 并发 payOrder 下 `rest` 可能丢失更新，与 `room_inventory` 不一致 | `testConcurrentPayOrder` 验证了 `rest` 结果正确，但依赖 `room_inventory` 先限流 |
| **order_info 无行锁** | `OrderServiceImpl.payOrder()` / `cancelOrder()` | 同一订单并发 pay / cancel 可能双写 | 未覆盖 |
| **checkOut 不变更订单状态** | `CheckInServiceImpl.checkOut()` | 退房后 order 仍为 CHECK_IN，理论上可重复 checkOut | 未覆盖 |
| **SimpleDateFormat 非线程安全** | `RoomInventoryServiceImpl` 的 `static final DATE_FMT` | 并发格式化可能产生错误日期 | 未覆盖 |

## 6. OrderStatus 命名规范

### 6.1 现状：三处定义不一致

| 状态码 | `OrderStatus` 枚举 | `schema.sql` 注释 | `test-schema.sql` 注释 |
|--------|-------------------|-------------------|----------------------|
| -3 | `WAS_DELETED`（已删除） | "deleted" | — |
| -2 | `OVERTIME`（支付超时） | — | — |
| -1 | `WAS_CANCELED`（已取消） | "canceled" | — |
| 0 | `UNPAID`（未付款） | "ordered" | "unpaid" |
| 1 | `PAID`（待入住） | "paid" | "paid" |
| 2 | `CHECK_IN`（已入住） | "consumed" | "checked_in" |

### 6.2 与 README 功能清单的对照

| README 功能描述 | 对应操作 | 当前 OrderStatus | 差异 |
|----------------|---------|-----------------|------|
| "预订客房" | `addOrder` → `payOrder` | UNPAID → PAID | README 用"预订"，代码用 UNPAID/PAID，语义一致 |
| "入住登记" | `checkIn` | PAID → CHECK_IN | 一致 |
| "结账 / 退房" | `checkOut` | **无对应状态** | ⚠ **README 有退房功能，但 OrderStatus 缺少 CHECK_OUT** |
| "预订信息管理" | CRUD on orders | — | 管理界面功能，无特殊状态 |

### 6.3 RoomStatus 与 OrderStatus 的映射关系

| RoomStatus 枚举 | 对应 OrderStatus | 触发操作 |
|----------------|-----------------|---------|
| `AVAILABLE(1)` 空闲 | — | checkOut 恢复 |
| `ORDERED(2)` 被预订 | UNPAID(0) 或 PAID(1) | ⚠ **当前代码未在 payOrder 中更新 room_status** |
| `IN_USE(3)` 已入住 | CHECK_IN(2) | checkIn 设置 |

> ⚠ `RoomStatus.ORDERED` 在枚举中存在，但 `payOrder` 并未将任何物理房间标记为 ORDERED。
> 这是设计意图：付款时只占用"库存配额"（room_inventory.ordered++），不分配具体房间；
> 具体房间在 checkIn 时才通过 `roomService.inRoom()` 随机分配。

### 6.4 建议命名规范（待评审后实施）

| 状态码 | 建议枚举名 | 建议中文名 | 说明 |
|--------|-----------|-----------|------|
| -3 | `DELETED` | 已删除 | 去掉 `WAS_` 前缀，与其他枚举风格统一 |
| -2 | `OVERTIME` | 支付超时 | 保持不变 |
| -1 | `CANCELED` | 已取消 | 去掉 `WAS_` 前缀 |
| 0 | `UNPAID` | 未付款 | 保持不变（schema 注释改为 "unpaid"） |
| 1 | `PAID` | 待入住 | 保持不变 |
| 2 | `CHECKED_IN` | 已入住 | 改为过去分词，与 `CANCELED`/`DELETED` 风格统一 |
| **3** | **`CHECKED_OUT`** | **已退房** | **新增** — 对应 README "结账"功能 |

> 本节为命名建议，实施需同步修改枚举类、所有 `getCode()` 引用点、前端展示逻辑和数据库注释。

## 8. 总结：两套库存的对账关系

在任何时刻，对于任意 `(type_id, inv_date)`，以下等式应成立：

```
room_type.rest ≈ total_on_any_date - SUM(ordered + occupied)  -- 近似，因 rest 无日期维度
```

但由于以下设计差异，**两套数值可能出现短暂不一致**：

| 维度 | room_type.rest | room_inventory |
|------|---------------|----------------|
| 粒度 | 房型级（无日期） | 房型 × 日期 |
| 并发控制 | 无（read-modify-write） | 乐观锁（version） |
| 写入时机 | payOrder / cancelOrder / checkOut | payOrder / cancelOrder / checkIn / checkOut |
| 失败语义 | `updateRest` 返回 -1 即停 | 乐观锁重试 3 次后返回 -2 |

> **核心建议**：`room_type.rest` 应逐步退化为派生字段（从 `room_inventory` 聚合查询），
> 而非独立维护。在此之前，任何涉及 `rest` 的前端展示应以 `room_inventory.available` 为准。
